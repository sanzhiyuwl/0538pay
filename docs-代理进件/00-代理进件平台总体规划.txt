====================================================
0538pay 代理进件平台 · 总体规划（自研扩展，非 epay 精仿）
====================================================
建档：2026-07-28
定位：0538pay 除「收单」外的第二条营收线。平台作为微信支付服务商（sp_mchid），
      通过「代理」这一分销层，把「特约商户进件（开通微信收款）」作为一项收费服务卖出去。
      收单不是唯一赚钱方向，进件是并列的一条独立业务线。

⚠️ 精仿边界（重要）：
   本模块是 0538pay 的【自研扩展】，彩虹易支付 epay 原生没有代理、没有名额、
   没有进件功能（epay 里 sub_mchid 只是微信服务商版收单插件的一个配置项）。
   因此本模块不纳入 docs/epay功能对比清单.txt 的精仿打勾体系，单独在 docs-代理进件/ 下管理。
   与 epay 精仿目标不冲突：精仿继续在 docs/ 下推进，本线并行独立发展。

====================================================
一、业务模型（已与用户确认）
====================================================

角色：
  平台（我方）   —— 微信支付服务商，持 sp_mchid，是唯一能调进件接口的一方
  代理           —— 平台的分销层，招特约商户、发起进件，赚差价。挂在 SaaS/控制台体系下由平台开通
  特约商户       —— 被进件的商户，进件成功后拿到自己的 sub_mchid，走平台 sp_mchid 收款

三种进件发起方式（2026-07-28 补充：客户自助）：
  1. 平台后台代填 —— 平台运营在后台替客户填资料、发起进件
  2. 代理控制台代填 —— 代理在控制台替自己名下客户填资料、发起进件
  3. 客户自助进件（新增）—— 代理/平台把【专属进件链接或二维码】分享给客户，
       客户在手机或电脑上自己打开、填资料、传证件、提交。链接绑定归属代理，
       客户自助提交的进件单自动归到该代理名下。三种方式最终都落到同一张
       pay_submch_enroll 表，只是 source 字段不同（1平台代填/2代理代填/3客户自助）。
       ★ 必须同时支持 PC + H5（一套响应式公开页吃两端）。

核心变现：卖「进件名额」。一个特约商户成功进件 = 消耗一个名额 = 一笔 200 元的生意。
   ★ 关键锚点：不管哪条路径，特约商户开户永远付 200 元；平台每成功进一户稳赚 100，代理稳赚 100。
   区别只是平台这 100 是「提前收」还是「事后分」。

两条路径：
  路径一 · 代理预购名额（需要「名额钱包」存储机制）
    - 代理提前向平台批发买名额，价 100 元/个（批发价，待定可配）→ 平台当场收 100
    - 代理招来的商户进件时，直接扣 1 个名额，商户仍付 200 元，这 200 全归代理
    - 代理净赚 = 200 − 100（屯名额成本）= 100
    - 平台这一路只赚一道：卖名额的批发价 100

  路径二 · 代理无名额，商户自付（兜底路径）
    - 代理没买名额时，商户进件付 200 元
    - 进件成功（微信审核通过）后，这 200 分账：平台 100，代理 100
    - 代理净赚 100，平台赚 100

  两条路径最终分配一致（平台 100 / 代理 100），只是付款时点与形式不同：
    路径一 = 平台预收批发款，商户 200 全归代理
    路径二 = 商户付 200 进平台，进件成功后平台返代理 100

结算触发点（已确认）：
  以「微信真进件成功」为准 —— 微信审核通过、拿到 sub_mchid，才算这一单成功，才结算/扣名额。
  （平台内部标记完成不算数，必须真进件成功。依赖平台真有 sp_mchid + 进件接口跑通。）

定价杠杆（都要做成后台可配，不写死）：
  - 名额批发价（默认 100，待定）
  - 商户开户零售价（默认 200，待定）
  - 路径二分成比例（默认平台 100 / 代理 100，待定）

====================================================
二、资金流（部分待用户拍板，标 [待定]）
====================================================

路径一（代理预购名额）：
  1. 代理充值买名额 → 走平台【收单能力】收这笔批发款（复用现有支付下单）→ 名额钱包 +N
  2. 商户进件付 200 → [待定] 这 200 是「进平台账再全额转给代理」还是「直接进代理账」？
       方案 a：商户付款进平台账，平台代收后全额转代理（平台账面过账，便于留痕/风控）
       方案 b：商户直接付给代理（平台不碰这笔钱，只管扣名额）
  3. 进件成功 → 扣 1 个名额，无 200 分账（代理利润来自他自己收的 200）

路径二（商户自付）：
  1. 商户进件付 200 → 走平台【收单能力】进平台账
  2. 进件成功（微信审核通过）→ 平台结算：代理 +100（进代理余额/可提现），平台留 100
  3. [待定] 若进件失败/被驳回，商户这 200 是否退款？退多少？（建议：失败全额退商户，做成可配）

★ 连接点：两条路径的收钱都复用你已做好的收单主链（下单/收款/回调）。
   这正是「多维度平台」的体现：收单不只服务商户日常交易，也服务平台自己卖名额/卖开户服务。

三、数据结构草案（后端 Go + GORM，表名待定）
====================================================

Agent（代理）:
  id, name, 登录账号, 密码(bcrypt), 联系方式, 状态(启用/停用),
  permissions(已开通权限点集合，可扩展权限体系；含内置 enroll 进件代理 /
    acquire 收单代理占位，替代早前零散的 can_enroll/can_acquire 布尔字段),
  创建时间, 备注
  ★权限设置（2026-07-28 新增）：代理能用哪些功能由平台逐项开通的权限决定——
    权限开通啥代理就有啥；后续加新功能只需登记一个权限点 key，平台勾选即生效，
    代理端骨架不改。详见 01 文档「一之二、代理权限设置」。

AgentQuotaWallet（名额钱包，路径一用）:
  agent_id, balance(当前名额数), 累计购买, 累计消耗, 更新时间
  （余额变动走流水表，不裸改）

AgentQuotaLog（名额流水）:
  id, agent_id, type(purchase 购买 / consume 进件消耗 / refund 退回),
  change(+/-N), before, after, 关联进件单号/充值订单号, time, remark

SubMerchantEnroll（特约商户进件申请）:
  id, 进件单号(幂等键), agent_id(归属代理), 商户名称/主体类型,
  营业执照/证件/银行账户等资料字段(参照微信进件接口，敏感字段加密存),
  path(1 预购名额 / 2 商户自付), retail_amount(商户付的 200),
  pay_order_no(商户开户费/名额批发的收款单号),
  wx_applyment_id(微信申请单号), wx_sub_mchid(成功后的 sub_mchid),
  status(草稿/已提交/审核中/已驳回/已完成), 驳回原因, 提交时间, 完成时间,
  source(发起方式：1 平台代填 / 2 代理代填 / 3 客户自助),
  invite_code(自助进件时来源的邀请链接 code，回填便于追溯)

EnrollInvite（进件邀请链接 / 二维码，客户自助用）:
  id, code(唯一，URL 里用；如短随机串), agent_id(归属代理，0=平台自己发),
  name/备注(便于代理区分给了哪个客户), status(启用/停用/已失效expired),
  first_access_at(客户首次打开时间，为空=还没人点),
  expire_at(失效时间；★不是从打开死算，而是锚定"终态事件"，见下★，为空=不倒计时/仍有效),
  累计打开数, 累计提交数, 创建时间
  （二维码 = 该 code 对应公开页 URL 的 QR，前端生成即可，不必单独存图）
  ★ 生命周期（2026-07-28 修订：24h 锚定终态事件，不从打开死算）：
    - 链接创建/审核中/待账户验证等"进行中"状态 → expire_at 保持空，链接一直有效，
      不倒计时（避免微信审核周期拉长把客户卡死）。
    - 出现【终态事件】时才置 expire_at = 事件时刻 + 24h（时长后台可配）：
        · 待支付超时自动关单       → 从关单时刻 +24h
        · 已支付后被驳回 / 退款完成 → 从"收到该返回结果"时刻 +24h
      谁先到从谁算；24h 内客户可用同一链接二次发起（重新建单再走一遍）。
    - 超过 expire_at → status=expired 自动失效，客户无法自助复活，必须联系代理/
      分享人重新生成新链接或二维码。定时任务扫到期链接置 expired。

EnrollPricing（进件计费规则，后台可配）:
  wholesale_price(名额批发价 100), retail_price(开户零售价 200),
  platform_share(路径二平台分成 100), agent_share(路径二代理分成 100),
  fail_refund(失败是否退商户 + 退多少)

EnrollSettleLog（进件结算流水，路径二用）:
  id, enroll_id, agent_id, amount(代理得 100), platform_amount(平台得 100),
  settle_time, 关联收款单号

商户归属：SubMerchantEnroll.agent_id 标记每户属于哪个代理，代理端按此做数据隔离
          （代理只能看/管自己名下的进件与商户）。

四、进件流程（微信特约商户进件 · APIv3 合作伙伴）
====================================================
微信侧接口（服务商体系，路径 APIv3/合作伙伴/子商户管理/特约商户进件）：
  - 提交申请单（Applyment）
  - 文件/图片/视频上传（证件材料）
  - 按申请单号 / 业务申请编号查询申请状态
  - 查询/修改结算账户
技术复用：复用 internal/channel/wxbase 的 V3 请求签名、平台证书验签、
          RSA-OAEP 敏感字段加密（进件里身份证号、银行账号正是用它加密）。
  ★ 但不实现 PaymentChannel 收单契约 —— 进件是独立 service 模块，
    不进渠道 registry、不进收单主链、不进收银台、不进插件卡片墙。

平台资质卡点：
  只有「普通服务商」能调进件接口，平台须先有 sp_mchid + 开通进件权限。
  若暂无凭证 → 先搭骨架（UI+流程+数据模型+接口代码就绪），对齐项目里其它
  「代码就绪待凭证」的做法，拿到 sp_mchid 后再连真接口真跑。

五之一、进件配置三处归位（关键：单一数据源，别混）
====================================================
「进件配置」不是一样东西，拆成三类，各归其位：

1. 代理是谁 / 名额 / 佣金对象 → 【代理控制台】（本模块）
     平台运营管「人」：开通代理、权限、名额售卖、佣金结算。

2. 平台微信服务商凭证（sp_mchid / 商户私钥 / 证书序列号 / APIv3密钥 / 平台证书公钥）
   → 【系统设置·平台级单例区】（存 pay_config，ConfigService 统一管，复用 C8 基建）
     理由：进件永远是「平台以服务商身份」调微信，与哪个代理/商户无关，
           全平台唯一一套。★ 且与「微信服务商模式收单」共用同一份 sp_mchid，
           必须单一数据源，绝不能配两遍（配两遍=改一个忘一个=线上事故）。
     ——即使收单代理暂不做，凭证也按「平台服务商身份单例」设计，为将来共用留好。

3. 进件业务参数（名额批发价/开户零售价/路径二分成/失败退款规则）
   → 【代理控制台·进件业务设置页】
     这门生意的运营参数，天然属于进件模块，平台运营视角可改。

一句话：控制台管「代理是谁」；系统设置管「平台的服务商身份」；进件设置管「这单怎么算钱」。

代理进件涉及的端（三端并存）：
  - 平台侧（后台/控制台 /console）：平台运营视角。开通代理、配置计费规则、
    审核/跟踪【所有】进件、看全局名额售卖、也能替客户发起进件与生成邀请链接。
  - 代理侧（独立代理端 /agent）★已定：单开一个端★：仿商户中心 /m 的做法，
    独立 AgentLayout + 代理登录态（代理账号密码/JWT，不与 admin/商户混）。
    代理登录后【只看自己名下】：名额余额、我的进件单、我的邀请链接/二维码、我的佣金。
    数据隔离靠登录代理的 agent_id 过滤，不是靠页面权限拼凑。
  - 客户侧（公开页 /enroll/:code，免登录，PC+H5）：客户扫码或点链接进入自助进件页，
    填资料、传证件、提交；提交后可凭进件单号+手机号查询审核进度。
    此端无登录态，靠链接 code 绑定的 agent_id 自动归属代理。
  ✓ 已定（2026-07-28）：代理端【单开一个端 /agent】，不挂 /console 按角色隔离。
    理由：/console 是平台运营视角（管所有代理），与代理只看自己名下是两回事，
    混在一套页面里权限过滤处处小心易漏；独立端职责边界最清晰、数据隔离最硬。

====================================================
三之一、客户自助进件（公开页，PC + H5）
====================================================
入口：代理或平台在控制台生成【进件邀请链接】(/enroll/:code) 及其二维码，分享给客户。
  code 绑定 agent_id；客户从该链接进来提交的进件单自动归属这个代理。

公开页流程（免登录，★付费前置★）：
  1. 客户扫码/点链接 → 打开 /enroll/:code（PC 与 H5 同一响应式页面）
  2. 校验 code 有效（存在/启用/未过期），无效则提示失效
  3. 第1步 填最基础信息（商户名/联系手机）→ 点"创建进件单"
     → 生成 pay_submch_enroll（source=3 自助，agent_id=code 归属，invite_code=code，
       status=待支付）→ 立即调起收款（复用现有收单主链）
  4. 客户付开户费 → 支付回调确认到账 → status=已支付待完善 → 放行下一步
  5. 第2步 填全套主体资料 + 上传证件（营业执照/身份证/银行账户等，字段对齐微信进件接口）
     → 提交 → 调微信进件接口，status=审核中
  6. 客户可凭「进件单号 + 联系手机号」在公开页查询审核进度（待支付/审核中/驳回/已完成）
  ★ 付费时点已定：进件第一步创建单即收费，付款成功才放行填全套资料/提交微信审核。
    待支付超时自动关单；已支付后放弃或被驳回支持原路退款。

链接生命周期与二次发起（2026-07-28 第五轮补充，第六轮修订 24h 锚点）：
  - 有效期锚点：24 小时【不从打开死算】，而是锚定"终态事件"发生后才起算：
      · 待支付超时自动关单       → 从关单时刻起 24h
      · 已支付后被驳回 / 退款完成 → 从"收到该返回结果"时刻起 24h
    进行中（审核中/待账户验证等，未拿到任何驳回或成功返回）→ 不倒计时，链接一直有效。
    这样即便微信审核周期拉长，也不会把还在等结果的客户误关。时长后台可配（默认 24h）。
  - 二次发起：终态事件后的 24h 内，客户可用【同一链接】重新建单再走一遍（不必找代理）。
  - 到期失效：超过该 24h，链接 status=expired，客户打开提示"链接已失效"，无法自助复活。
    想再进件必须【联系代理/当初分享链接的人重新生成并分享新链接或二维码】——
    重开入口唯一收敛在代理/平台侧，客户端无自助重开。
  - 实现要点：公开页每次访问校验 expire_at（为空=仍有效）；终态事件(关单/驳回/退款完成)
    发生时由 service 写 expire_at=now+24h；定时任务(复用现有 scheduler)扫到期置 expired；
    代理端/控制台"我的邀请码"页可一键重发/新建替换。

安全（免登录公开接口，必做）：
  - code 校验 + 有效期/停用开关，防止链接被无限复用
  - 图形验证码 / 手机验证码防刷提交
  - 上传限制文件类型与大小；敏感字段（身份证号、银行账号、手机号）前端传后端后
    用 RSA-OAEP 加密存（复用 wxbase 敏感字段加密），不明文落库
  - 提交接口限流；EnrollInvite 记打开数/提交数便于监控异常

PC + H5：一套响应式公开页自适应两端（复用项目现有 isH5/移动端判断经验），
  移动端优先保证证件拍照上传顺畅。
